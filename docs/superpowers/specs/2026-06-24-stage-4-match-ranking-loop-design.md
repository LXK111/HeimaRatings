# 阶段 4：比赛录入与排名计算闭环设计

## 修改记录

## 目标

阶段 4 验证一个最小但真实的业务闭环：裁判台录入比分后，用户可以立即用当前页面中的比赛数据重新计算分武器排名，并看到 Ranking Engine 返回的结果。

本阶段不验证数据库持久化，也不保存排名快照。这样可以先确认“录入数据是否能影响排名结果”这一核心链路，避免把阶段 4 扩大为数据层工程。

## 范围

- 改造 `app/tournaments/[id]/matches/page.tsx`，接入客户端交互工作台。
- 新增比赛录入表单，支持选择比赛项目、轮次、双方选手、比分。
- 新增算法和武器类型选择，支持调用 `/api/rankings/calculate`。
- 新增页面内排名结果展示，展示本次计算的排名、积分、战绩。
- 新增错误、加载、空结果状态。

## 非目标

- 不接入 Supabase。
- 不持久化新增比赛。
- 不保存 `ranking_snapshots`。
- 不改造公开榜单和嵌入榜单。
- 不做完整赛事编排、签表生成或淘汰赛晋级逻辑。

## 推荐方案

采用页面临时闭环：

- 初始比赛通过 `/api/tournaments/[id]/matches` 读取。
- 新增比赛先调用 `POST /api/tournaments/[id]/matches` 做服务端校验并生成草稿结构。
- POST 成功后，将返回的比赛草稿追加到页面本地状态。
- 点击“重新计算排名”时，页面按所选武器筛选当前本地比赛，组装完整 `RankingEngineInput`。
- 页面将完整输入提交给 `/api/rankings/calculate`。
- 页面展示 Ranking Engine 返回的本次计算结果。

## 架构

### 页面入口

`app/tournaments/[id]/matches/page.tsx` 继续作为路由入口，负责渲染 `AppShell` 和引入客户端工作台组件。

### 客户端组件

新增 `components/matches/match-workbench.tsx`：

- 管理比赛列表本地状态。
- 管理表单状态。
- 管理所选算法和武器类型。
- 调用比赛 API 和排名计算 API。
- 将计算结果转换为页面可展示数据。

### 数据辅助

必要时新增轻量辅助函数，集中处理：

- 根据武器类型筛选比赛。
- 按轮次将比赛分组为 `RankingEngineMatchInput[][]`。
- 从现有选手分武器积分组装 `RankingEnginePlayerInput[]`。
- 将 `RankingEngineOutput.rankings` 映射为排名表格行。

## 数据流

1. 页面打开后加载当前赛事的 Mock/API 比赛数据。
2. 用户填写项目、轮次、选手和比分。
3. 页面提交到 `POST /api/tournaments/[id]/matches`。
4. API 返回比赛草稿，页面追加到本地比赛列表。
5. 用户选择算法和武器类型，点击重新计算。
6. 页面根据当前本地比赛列表构造完整 `RankingEngineInput`。
7. 页面调用 `POST /api/rankings/calculate`。
8. 页面展示本次计算结果，不覆盖静态 Mock 排名快照。

## 校验与错误处理

- 双方选手不能为空。
- 双方选手不能相同。
- 比分必须是有限数字且不小于 0。
- 所选武器下至少需要一场比赛才能计算。
- Ranking Engine 调用失败时展示错误信息。
- 计算中禁用提交按钮，避免重复请求。

## 测试与验证

- 运行 `npm run check`。
- 运行 `npm run build`。
- 手动验证比赛页面可加载初始数据。
- 手动验证新增比赛后列表立即追加。
- 手动验证新增比赛会参与当前页面的本次排名计算。
- 手动验证无效比分、重复选手、Ranking Engine 错误都有可见反馈。
